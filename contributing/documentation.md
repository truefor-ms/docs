# Documentation standard

**Established:** 6 November 2026. Applies to documentation and reports maintained in this repository.

## Language and delivery

- Write all newly authored documentation, reports, navigation and interface text in **English**.
- Deliver reports as **HTML** and register them in the [Docs Hub](../index.html). Markdown-only reports are not a completed delivery.
- Keep titles and descriptions factual. Use minimal promotional copy and no slogans in the documentation interface.
- Include existing documentation in the hub, including the build path, implementation guides, references, brand and working rules.
- Preserve supplied original materials byte-for-byte and in their original language. Label them as source materials rather than silently translating or replacing them.

## Sources and HTML pages

Markdown is the editable source for authored documents. The matching HTML is the reading and report-delivery format. Both are versioned; regenerate HTML whenever the source changes. Do not independently edit generated prose in HTML.

`site/catalog.json` records each document's title, category, kind, source date and description. `site/build.py` creates the home page, all registered reading pages and a complete file inventory. Registered `README.md` files become `index.html`; other Markdown documents keep their basename with `.html`. Links between registered documents are rewritten to HTML.

Open `index.html` from a complete checkout. Keep relative assets and folders together. Search filters titles and descriptions locally. Reading, navigation and file access remain available without JavaScript; search and the print button are progressive enhancements. This is an offline site bundle, not a promise that each page is a self-contained attachment.

## Presentation

Use the original logo master as the visual reference: warm canvas, green ink, Rubik body text and Linux Libertine Display headings. Use the approved outlined logo, including its independent dot. Its font is not the document heading font.

Shared presentation lives in `site/docs.css`; optional behavior lives in `site/docs.js`. Avoid per-report visual themes. Use a readable measure, section navigation, source links, scrollable comparison tables, visible keyboard focus, responsive layouts and print styles. The current hub uses the light reference palette; it does not establish a new product-wide theme system.

Fonts and artwork are referenced from the preserved package. Keep source notices accessible. Never modify `brand/handoff/` to adapt a report.

## Report content

Every report should state its date, scope, method, findings, recommendations, evidence links and verification limits. Distinguish observed behavior, source claims, proposals and unknowns. Keep historical observations tied to their original review date; an HTML conversion is not a new audit.

Keep machine-readable evidence such as JSON alongside the relevant report and link it directly. HTML is the report; raw evidence is supplementary. The all-files inventory provides access to assets, licenses, scripts and records that are not prose documents.

## Build and check

From the docs repository, install the pinned build dependency in your preferred Python environment:

```powershell
python -m pip install -r site/requirements.txt
python site/build.py
python site/build.py --check
```

The check detects stale HTML, unregistered authored Markdown documents, broken local links and missing HTML anchors. It does not validate external website availability. Original package content is never regenerated by this builder.

After presentation changes, inspect the hub and representative long documents on desktop and mobile, exercise search/category/reset and section navigation, and check for overflow. Check print styling separately from on-screen layout; do not claim a physical print proof from browser inspection.

Register new documents, rebuild and verify before committing. Follow the [contribution rules](README.md): English Conventional Commits, the required Trueforms author/committer identity, and pushes only through `formtrue` when requested.

## Project UI skills

The project records upstream references rather than maintaining copied skill releases.

- [building-components](https://github.com/vercel/components.build/tree/main/skills/building-components): component architecture and contracts. Treat this as an architectural reference only; its Tailwind and TypeScript recipes are outside the project's accepted approach.
- [web-design-guidelines](https://github.com/vercel-labs/agent-skills/tree/main/skills/web-design-guidelines): interface implementation reviews.
- [accessibility](https://github.com/addyosmani/web-quality-skills/tree/main/skills/accessibility): accessibility implementation and verification.
- [Impeccable](https://github.com/pbakaus/impeccable): visual hierarchy and design refinement.
- [better-layout](https://github.com/jakubkrehel/skills/tree/main/skills/better-layout): grouping, responsive layout, text growth, and RTL.

Consult the current upstream instructions and relevant supporting references before using a skill. Existing local installations are conveniences, not authoritative snapshots. Use only task-relevant guidance, preserve the approved brand and technology choices, and do not use a skill version that requires Tailwind CSS or TypeScript. Upstream references are not blanket approval of future changes.

No project installer or repository-vendored skill bundle is required. Skills may be read from their sources or used through a compatible local installation. Report unavailable references as a verification limitation rather than claiming they were reviewed.
